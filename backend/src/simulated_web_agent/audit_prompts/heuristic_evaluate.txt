## Nielsen's 10 Heuristics (reference only — reason in English)

1. Visibility of system status — Does the system keep users informed about what is happening?
2. Match between system and the real world — Does the system speak the users' language?
3. User control and freedom — Can users easily undo mistakes and navigate freely?
4. Consistency and standards — Are conventions followed consistently?
5. Error prevention — Does the design prevent problems before they occur?
6. Recognition rather than recall — Is information visible rather than requiring memorization?
7. Flexibility and efficiency of use — Are there shortcuts for experienced users?
8. Aesthetic and minimalist design — Is irrelevant information absent?
9. Help users recognize, diagnose, and recover from errors — Are error messages clear and helpful?
10. Help and documentation — Is support available and easy to find?

## Standard conventions are NOT defects — do not report these

These are normal, expected behaviours across e-commerce sites. Reporting them as
usability problems is a false positive (real site teams reject them):
- A guest showing a login / registration prompt at checkout or account actions.
  Requiring an account to buy is a business choice, not a bug.
- A primary button (e.g. "Do koszyka") disabled until a REQUIRED option is
  chosen (size, variant, refund type). Its discoverability may at most be
  "drobny" IF the observation shows no hint of what is missing — never critical.
- A two-step or overlay search (an icon/box that opens a search panel). The
  pattern itself is conventional; only report it if the observation shows the
  search genuinely returning wrong/empty results for a valid query.
- An error message after submitting INVALID or made-up credentials. The site
  correctly rejecting a bad login is correct behaviour, not a defect.
- A cart shown as a count/number rather than a basket glyph, when an accessible
  label (e.g. "Koszyk, liczba produktów: N") is present in the observation.
- An "added to cart" toast reporting the count added IN THIS ACTION (e.g.
  "Dodano do koszyka: 1 produkt") that differs from the cart icon's RUNNING
  TOTAL. These are different numbers by design — per-action count vs. cumulative
  total. Only report a defect if the cart icon's own total is itself wrong.
- Multiple checkout entry points that look similar (e.g. "Do kasy" vs. "Złóż
  zamówienie jako gość") are intentionally DIFFERENT paths (member vs. guest
  checkout), not redundant or broken buttons. Only report a defect if a
  SPECIFIC chosen path, once clicked, fails to advance.

- A cookie / consent / privacy notice. Every EU site shows one; it is a legal
  requirement, not a usability defect, and the reviewer of this tool had never
  once hit it as a problem. Only report it if the observation shows the notice
  itself is genuinely unusable to a person — e.g. it cannot be dismissed at all,
  or it permanently covers the content after a choice was made. "A banner
  appeared" is never a finding.
- A bot-detection or security-verification screen: Cloudflare "Performing
  verification" / "Checking your browser", a CAPTCHA, "verify you are human",
  DataDome, PerimeterX, Imperva. These appear BECAUSE the visitor is automated;
  a real person is waved through in a second or never sees them at all. Never
  report them as site defects, and never recommend the site change its bot
  protection — that recommendation was the single clearest error in the first
  external review of this tool. If the whole session was spent on such a screen,
  you observed nothing about the site: return no findings rather than inventing
  some from the challenge page.
- Anything describing the AUTOMATION failing rather than the site: a click that
  "did not register", an element that "could not be found", a step that "timed
  out", a repeated attempt that "had no effect". These are this tool's own
  interaction failures. A real user with a mouse would not have hit them, so
  they say nothing about the site and must never become a finding — whatever the
  session reflections say about them.
- A complaint that follows from the persona's own preference ("I prefer physical
  shops", "I rarely buy online", "I like to see things in person"). It describes
  the person, not the site.
- A limit inherent to the medium: a screen cannot be touched, a garment cannot be
  tried on, a true colour or the feel of a fabric cannot be judged online. That is
  true of every website.

Still fully reportable (do NOT suppress): an action the site ALLOWS and then
fails on (e.g. add-to-cart succeeds then errors), genuinely broken links, real
data loss, content that is objectively unreadable — and information the site
could supply and withholds (no material composition, no dimensions, a single
photo, no care instructions), even when the persona's reflection is about not
being able to touch the product.

## Output format

After your English reasoning, output a JSON array. Each element must follow this schema exactly:

```json
[
  {{
    "heuristic_id": 1,
    "heuristic_name": "Widoczność statusu systemu",
    "severity": "<krytyczny | poważny | drobny — see the scale above>",
    "url": "https://example.com/search",

    "evidence": "Po wpisaniu zapytania w wyszukiwarkę i naciśnięciu Enter strona nie pokazała żadnego wskaźnika ładowania ani wyniku.",
    "recommendation": "Dodać widoczny wskaźnik ładowania lub natychmiastowy komunikat po wysłaniu zapytania.",
    "confidence": "<high | medium | low — see the rule below; do not default to high>"
  }}
]
```

Polish names for all 10 heuristics:
1. Widoczność statusu systemu
2. Zgodność systemu z rzeczywistością
3. Kontrola użytkownika i swoboda działania
4. Spójność i standardy
5. Zapobieganie błędom
6. Rozpoznawanie zamiast zapamiętywania
7. Elastyczność i efektywność użytkowania
8. Estetyczny i minimalistyczny design
9. Pomoc w rozpoznawaniu i naprawianiu błędów
10. Pomoc i dokumentacja

Rules:
- Only include findings where there is concrete evidence in the session data.
- If a heuristic has no violation, omit it entirely.
- "step" is REQUIRED for every finding. Observations and actions are prefixed with "[step N]" markers — cite the exact step number where the issue is visible. A finding without a real step citation will be discarded as unverifiable.
- "url" is REQUIRED — copy the URL shown in the "[step N]" line you are citing.
- "evidence" must quote or closely paraphrase the observation text of the cited step — never describe things that are not present in the session data.
- All string values — heuristic_name, evidence, recommendation — must be written in Polish.
- "confidence" is REQUIRED: "high" only when the observation text you quote directly and unambiguously shows the problem; "medium" when it is a reasonable inference from what you can see; "low" when the interaction may have failed for reasons other than the site (e.g. the element did not respond). Do not claim "high" for a problem you inferred rather than observed — "high" is a claim that the quoted evidence speaks for itself. If most of your findings are "high", you are not discriminating; re-read your own evidence and ask which ones you actually watched happen.
- Output valid JSON only after your reasoning. Do not wrap it in markdown fences in the final JSON block.
